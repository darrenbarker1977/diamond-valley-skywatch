# Location-aware weather

The selected observing coordinates and timezone drive every request. Environment and Climate Change Canada’s public MSC GeoMet city-page forecast is primary where a Canadian timezone and a closely matching forecast point or area are available. The app queries a bounding box around the selected coordinates, chooses the nearest supplied forecast area within 2.5 km, and displays its name, distance and forecast issue time. It never labels that area as an exact measurement at the telescope. Diamond Valley uses the official coordinate feed for 50.68, −114.25, which returns a Diamond Valley forecast point approximately 0.3 km away. The app never substitutes Okotoks or another town 20 km away.

Outside that coverage, when the nearest official area is stale, and after an official request failure, the Canadian GEM model family supplies coordinate-based numerical weather in Canadian coverage; Open-Meteo best-match remains the worldwide coordinate-based forecast. Near-term HRDPS data use a 2.5 km grid where available, with coarser regional/global grids beyond its short range. The returned grid location and model horizon limitation are disclosed. Both model requests use the selected coordinates and clock rules; mismatched or distant grid responses are rejected. Precipitation probability and missing fields remain explicitly attributed to Open-Meteo best-match. The UI explicitly identifies fallback. No Canadian forecast is reused for an Australian or other remote site. Location-keyed cache checks and message-origin checks remain in place; the forecast URL now carries the selected timezone as well as coordinates.

Official hourly conditions, temperature, precipitation probability and wind values are preserved without inferring numerical cloud cover. Later evenings use the actual night-wide official summary, not invented hourly openings or hourly temperatures derived from an overnight low. Classification of clear/few-cloud, variable-cloud and adverse conditions is a transparent app assessment, not an official astronomy verdict. Cloud, wind and precipitation remain cautions. Unknown conditions stay unverified. Source disagreement is shown when the primary and supplementary model yield opposing outlooks.

Open-Meteo numerical cloud layers, humidity, dew point, visibility and other existing model tiles remain available and explicitly labelled. The official hourly chart shows qualitative conditions, temperature and wind rather than a fake cloud percentage. When Open-Meteo fails, official forecast coverage can still be displayed; missing numerical details stay absent. If both sources fail, the existing dated cached forecast/offline handling remains.

The app refreshes its sources with the existing 30-minute, return, online and manual-refresh paths. Issued and downloaded times are distinct. Official hourly issues expire after 18 hours and night summaries after 36 hours; future issues, distant areas and mismatched coordinates/zones are rejected. Automatic source selection never overrides real sensor or alignment checks.

Night Mission, Ready check and same-eyepiece advice use the same provider-aware weather snapshot. Weather influences tour preference and cautions, never hides astronomical targets. Seen it retains the provider, condition, area, issue time and hourly/night-wide granularity when official data are used; numerical cloud cover remains null. Existing Open-Meteo and legacy sighting records and backups remain readable.

Data source: Environment and Climate Change Canada, MSC GeoMet OGC API `https://api.weather.gc.ca/collections/citypageweather-realtime/items`. Supplementary and worldwide forecast: Open-Meteo (CC BY 4.0). These are forecasts, not observed or guaranteed observing conditions. The official coordinate website feed has no browser CORS header. A repository Action therefore fetches and validates only the public default Diamond Valley point every 30 minutes and publishes a same-origin JSON cache. The client uses it only within 2.5 km and within three hours of download, with official issue-age limits as well. Other nearby official city-page API products are used only within 2.5 km. The provider, point/area distance and issue time stay visible. No key, untrusted CORS proxy or personal-location publication is required. No personal location is committed to the repository.

Tests use synthetic deterministic provider responses and block live ECCC calls in existing browser tests. Coverage includes source disagreement, worldwide switching, unavailable-provider fallback, official-only operation, stale/malformed/mismatched sources, timezone handling and historical sighting provenance.

## Green-light percentage rule

Green requires a model-derived window of at least two truly consecutive evening hours at no more than 25% total cloud. Wind speed, gust and precipitation probability must be available: sustained wind no greater than 15 km/h, gusts no greater than 25 km/h and precipitation probability no greater than 20%. Known snowfall, WMO fog/precipitation codes and model horizontal visibility below 10 km reject the hour. These are conservative app operating guidelines, not international telescope limits. A conflicting variable/cloudy/unverified official outlook or bright Moon cannot produce green. This is a conservative application guideline, not a universal astronomy standard. Qualitative clear text never becomes an invented cloud percentage. The badge, window label and displayed hourly percentages use the same qualifying model window; official hourly conditions, temperature and wind remain labelled alongside it. Green describes that window, not every hour of the night.

The cloud boundary is grounded in the meteorological FEW category (1/8–2/8 sky cover), not a claim that aviation weather is an astronomy quality standard. See the NWS Surface Weather Observing manual https://www.weather.gov/media/surface/WSOH8.pdf and ECCC astronomy guidance https://weather.gc.ca/astro/. Seeing and transparency are separate astronomical forecasts; horizontal meteorological visibility is not a substitute. The app explicitly treats unavailable specialist values as unknown and explains how planets and faint deep-sky targets have different requirements.

The public default-point cache is read from the repository’s current raw data first, with the bundled same-origin copy as a fallback. This makes scheduled weather updates available without waiting for a Pages rebuild after a bot commit. The fixed public feed contains no visitor locations; the same coordinate, age and issue-time checks apply to both copies. A main-branch push changing the updater or its workflow starts a refresh immediately; data-only bot pushes cannot trigger a loop.
